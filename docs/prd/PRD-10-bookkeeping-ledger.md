# PRD-10 — Bookkeeping / Studio Ledger

## 1. Objective

Provide practical operational bookkeeping for Studio37 by recording income, expenses, refunds, commission payouts, and manual adjustments in one traceable ledger.

This module is not intended to replace formal double-entry accounting or tax software in the initial product.

## 2. Ledger Entry Types

- Income
- Expense
- Adjustment
- Reversal/refund representation as defined by transaction source

## 3. Income Categories

Initial examples:

- Rehearsal
- Recording
- Mixing
- Mastering
- Equipment/Instrument Rental
- Additional Service
- Other Income

Categories should be configurable or at least extensible without changing historical records.

## 4. Expense Categories

Initial examples:

- Studio Operator Fee
- Recording Operator / Engineer Fee
- Equipment Maintenance
- Electricity / Utilities
- Equipment Purchase
- Consumables
- Rent
- Other Expense

## 5. Ledger Record

Each record should support:

- entry type
- category
- amount
- occurred date/time
- description
- payment method
- related booking ID when relevant
- related payment/commission/payout source when relevant
- related operator when relevant
- manual/source indicator
- actor
- created/updated timestamps

## 6. Source-Generated vs Manual Entries

### Source-generated

Examples:
- customer payment -> income ledger entry
- commission payout -> expense ledger entry
- refund -> financial reversal record

These records should retain a source ID and be idempotent so the same event cannot post twice accidentally.

### Manual

Owner or authorized user can record expenses/income not generated by a booking, such as equipment repair or electricity expense.

## 7. Edit/Delete Policy

Financial history should prefer correction/adjustment over destructive deletion.

If manual entry editing is allowed, changes require audit metadata. Entries generated from source transactions should not be freely edited independently of their source.

## 8. Summary & Reporting

Required period summaries:

- total income
- total expenses
- net operational result
- income by category
- expenses by category

Filters:

- date range
- type
- category
- payment method
- booking/operator reference
- search/description

## 9. Cash Basis

Initial bookkeeping should operate primarily on actual financial movement (for example, payment received) rather than treating a booking's full invoice amount as collected revenue before payment.

Outstanding customer balance is tracked in booking/payment financials, not falsely counted as cash received.

## 10. Commission Relationship

An earned commission is a liability-like operational amount but should only create the configured cash expense entry when it is actually paid/settled, unless the Owner later chooses an accrual-style reporting mode.

## 11. UX Requirements

- Summary cards for selected period.
- Dense transaction table on desktop.
- Clear Income/Expense distinction.
- Source link for generated records.
- Quick `Record Expense` action.
- Transaction detail shows who recorded it and why.
- Mobile layout prioritizes totals, filtering, and readable transaction cards.

## 12. Export Future Scope

CSV/spreadsheet export may be added later. Data structures should preserve enough clean fields to support export even if export is not required for first implementation.

## 13. Acceptance Criteria

- Owner can record manual income/expense.
- Valid booking payments can be traced into bookkeeping.
- Commission payouts can be traced into expenses.
- Source-generated entries cannot be duplicated by repeated processing.
- Period totals are consistent with filtered ledger entries.
- Outstanding unpaid booking balance is not counted as collected cash revenue.
- Financial corrections preserve auditability.
